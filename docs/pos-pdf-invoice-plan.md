# POS PDF Invoice — Implementation Plan

## Current Flow

`submitOrder()` in `pos-checkout.component.ts` currently has two paths:

1. **`config.printInvoice = true`**: calls `printOrder()` (opens browser print dialog with HTML receipt), then optionally clears items. The order is **not saved** to the backend in this path.
2. **`config.printInvoice = false`** (default): saves order → saves details → updates inventory → clears items. No PDF/print step.

## Problem

There is no way to get a PDF and automatically submit the order after printing. The user must manually choose one path or the other, and the print path never persists the order.

## Goal

When the user clicks **Submit order**:
1. Generate a professional PDF invoice with all order details
2. Open the browser print dialog (user can print or "Save as PDF")
3. After print completes/submits, automatically save the order to the backend and clear the POS

## Implementation Plan

### 1. New Service: `pos-invoice.service.ts`

Create a dedicated service to generate an HTML invoice string. This keeps the component clean and makes the invoice reusable.

**Location**: `src/app/services/vendei/v-invoice.service.ts`

**Responsibilities**:
- Accept order data (products, customer, payments, totals)
- Return a formatted HTML string ready for print/PDF
- Include:
  - Store header (logo, name, address)
  - Invoice title
  - Customer info (name, ID)
  - Line items table (qty, product name, price, subtotal)
  - Totals section (total, discount, amount paid, change returned)
  - Payment methods summary
  - Footer
- Use print-friendly CSS (thermal receipt size 80mm width)

### 2. Enhance `printOrder()` in `pos-checkout.component.ts`

**Changes**:
- Call the new invoice service to generate HTML
- Open a print window with the generated HTML (similar to current `printOrder()`)
- After the print window closes (detect via `onafterprint` or `beforeunload`), proceed to save the order
- If the print dialog is closed without printing, still save the order

### 3. Modify `submitOrder()` flow

**New flow**:
```
User clicks "Submit order"
  ↓
Generate invoice HTML (via v-invoice.service)
  ↓
Open print window with invoice
  ↓
User prints / saves as PDF / closes window
  ↓
Save order → Save details → Update inventory (current pipeline)
  ↓
Clear POS
```

### 4. Add `printInvoiceBeforeSubmit` config flag

**Location**: `v-config.service.ts`

Add a toggle so the behavior is configurable:
- `printInvoiceBeforeSubmit`: boolean (default: false)
- When `true`, the PDF+print flow runs before saving
- When `false`, the current direct-save flow runs

### 5. Changes to `pos-checkout.component.ts`

| Change | Details |

## Print Window Lifecycle

```typescript
printInvoiceAndSave(): void {
  const html = this.invoiceSvc.generate(this.selectedProducts, this.selectedCustomer, ...);
  const printWindow = window.open('', '_blank', 'width=400,height=600');
  printWindow.document.write(html);
  printWindow.document.close();

  // After print, save the order
  printWindow.onafterprint = () => {
    printWindow.close();
    this.saveOrderAndClear();
  };

  // Fallback for when print dialog is dismissed without printing
  const timer = setInterval(() => {
    if (printWindow.closed) {
      clearInterval(timer);
      this.saveOrderAndClear();
    }
  }, 500);

  // Trigger print
  printWindow.print();
}
```

## Edge Cases

| Case | Handling |
|------|----------|
| User cancels print dialog | Fallback interval detects window close, saves order anyway |
| User closes window without printing | Same as above — save proceeds |
| Browser blocks popup | Show user message to allow popups, or fall back to direct save |
| Network error during save after print | Error is caught by existing `error` handler in subscription |
| Multiple rapid submits | `printOrderCount` guard already prevents this |
| No products / empty order | `isOrderReadyToSubmit` prevents submission |

---

## Result Expected

1. User completes payment → "Submit order" button becomes active
2. User clicks "Submit order" → a print preview opens with a clean, formatted invoice
3. User prints (or saves as PDF) via the system print dialog
4. After the print dialog closes, the order is automatically saved to the backend
5. POS resets to empty state ready for next customer
6. No data loss — order is always saved, even if print is cancelled
