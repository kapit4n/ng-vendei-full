# Desktop installer and alpha releases

How Vendei becomes an installable Linux desktop application, and how to cut an
alpha. This is the follow-on to the development shell described in
[`../architecture/tauri-progress.md`](../architecture/tauri-progress.md).

## What the installer contains

A `.deb` (and an AppImage) that installs a self-contained application. Nothing
else has to be present on the machine — in particular **Node.js is not
required**, which is the whole point of packaging.

| Installed path | Contents |
| --- | --- |
| `/usr/bin/vendei` | The Tauri shell (Rust) |
| `/usr/lib/Vendei/backend` | The Node API, with production `node_modules` |
| `/usr/lib/Vendei/runtime` | A pinned Node runtime |
| `/usr/share/applications` | Desktop entry and icons |

The Angular bundle is compiled into the shell binary, so there is no separate
web root to serve.

## Why the backend is copied at first launch

`/usr/lib` is read-only for the user running the app, but the backend writes in
two places:

- **SQLite.** `models/index.js` resolves a relative `storage` against the
  backend root, and the bundled `config/config.json` uses `./database.sqlite`.
- **`public/uploads`.** `routes/upload-product-image.js` calls `mkdirSync` on it
  at *require* time, so a read-only tree makes the API throw while it is still
  mounting routes.

On first launch the shell therefore copies the bundled backend into
`~/.local/share/com.vendei.full/backend`, rewrites `config.json` so `storage` is
an absolute path beside it (`~/.local/share/com.vendei.full/database.sqlite`),
and runs the API from that copy. Migrations run there too, so the user's data
lives in app-data and survives reinstalling the package.

**The copy must be a real copy, not symlinks.** This was tried the other way and
shipped a subtle, silent failure: Node resolves a symlinked module to its real
path, so `__dirname` inside `models/index.js` pointed back into the read-only
bundle. Migrations then filled the overlay's database while the API opened a
different, empty one next to the bundle, and every request failed with
`no such table: StoreProfiles`. There is a regression test asserting the overlay
contains no symlinks.

Copying costs about 70 MB and takes well under a second. A version stamp
(`.vendei-version`, taken from the backend's `package.json`) rebuilds the overlay
when the bundled backend changes, rather than silently running an old copy.

## Migrations and seed data

`db:migrate` runs on every packaged launch. It is idempotent, so it doubles as
first-run schema creation and as the upgrade path between alphas.

**Seeding is opt-in.** A fresh install has tables but no products. Set
`VENDEI_SEED=1` to run `db:seed:all` for demonstration data:

```bash
VENDEI_SEED=1 /usr/bin/vendei
```

Seeding is not the default because a real shop should not start with demo
products.

## Staging the bundle resources

`src-tauri/backend` and `src-tauri/runtime` are build inputs, not source files.
They are git-ignored and regenerated by:

```bash
scripts/prepare-bundle-resources.sh                # stage anything missing
scripts/prepare-bundle-resources.sh --force        # re-stage everything
```

It is idempotent and is wired in as Tauri's `beforeBundleCommand`, so
`tauri build` always stages what it needs. It clones the backend at a pinned
commit, installs production dependencies, and downloads Node — verifying the
tarball against a **pinned SHA-256** so a compromised mirror cannot become a
shipped runtime.

Two details worth knowing:

- **`sequelize-cli` is a devDependency of the backend**, but the shell runs it
  directly to migrate. `npm ci --omit=dev` drops it, so the script adds it back
  explicitly. Note that `npm install --omit=dev <pkg>` silently installs
  *nothing* and still exits 0, which is why that flag is absent there.
- The script **fails loudly if any required backend file is missing**. A missing
  piece produces an app that installs cleanly and then dies on launch, which is
  exactly the failure mode to avoid.

## Building the installer locally

```bash
npm ci
npm run tauri:build -- --bundles deb          # or: deb,appimage
```

The result lands in `src-tauri/target/release/bundle/`. Requires the Linux build
dependencies listed in the workflow, and network access the first time (to stage
the backend and Node).

## Cutting an alpha

The version lives in `src-tauri/tauri.conf.json` and `package.json`, currently
`0.1.0`. Tag and push; the workflow does the rest:

```bash
git tag -a v0.1.0-alpha.1 -m "Vendei 0.1.0 alpha 1"
git push origin v0.1.0-alpha.1
```

`.github/workflows/release.yml` then:

1. stages the backend and Node runtime,
2. builds the `.deb` and AppImage,
3. **verifies the installed payload** actually contains `bin/www`, the migrated
   `sequelize-cli` entry, and the Node binary,
4. uploads the artifacts, and
5. publishes a GitHub **pre-release** for any tag containing a hyphen.

A tag without a hyphen (`v0.1.0`) publishes a normal release, so promoting an
alpha is just a new tag. To rehearse the build without publishing anything, run
the workflow manually from the Actions tab.

The Debian package version stays `0.1.0` even for `v0.1.0-alpha.1`, because a
hyphen in a Debian version means "revision" rather than "pre-release". The
pre-release nature is carried by the git tag, not the package version.

### Prerequisite: push the backend first

The workflow clones `inventory-nod` at the commit pinned in
`BACKEND_REF` (`.github/workflows/release.yml`) and in
`scripts/prepare-bundle-resources.sh`. The `/api/health` endpoint that the shell
polls before showing a window is **only in local backend commits so far**. Until
that commit is pushed, the clone cannot succeed and any installer built from an
older ref would wait forever for an endpoint that does not exist.

## Known limitations

- **No demo data unless `VENDEI_SEED=1`.** Deliberate, see above.
- **AppImage needs network at build time** to fetch `linuxdeploy`. The `.deb` has
  no such dependency.
- **The API is fixed to port 3999** and does not yet fail over to a free port.
  Two instances at once will conflict.
- **CORS on the API is `*`**, and the CSP allows `http://127.0.0.1:*`. Both are
  pre-existing and should be pinned to the shell's origin.
- **`libc`/`PR_SET_PDEATHSIG` is Linux-only**, so the kernel-level guarantee that
  the API dies with the shell is Linux-only. Packaging was validated on Linux.
- **Only `linux-x64` is wired up** end to end; the staging script knows the
  `arm64` Node checksum, but no workflow builds it.
- **No automatic updates.** Installing a new alpha replaces the package but keeps
  the app-data database, which is intentional.
